reverse-proxy-middleware 0.0.148

Project status

Use case

A small reverse proxy configured with a single JSON file. Each incoming request is passed on to one of the configured backends ("forwarders"). Before that, the proxy can ask third party services ("state APIs"), e.g. a bot filter like reCAPTCHA or friendlycaptcha or an authentication service, and answer the request itself depending on their responses. Request and response headers can be rewritten on the way through. All decisions are short JavaScript expressions inside the configuration.

Content

Installation

Install the command globally via npm and start it in the folder which holds your "configuration.json":

npm install --global reverse-proxy-middleware
reverse-proxy-middleware

Or run the container image and mount the configuration into it:

docker run \
    --name reverse-proxy-middleware \
    --publish 8080:8080 \
    --rm \
    --volume "$(pwd)/configuration.json:/application/configuration.json" \
    ghcr.io/thaibault/reverse-proxy-middleware:latest

"systemd.service" in this repository is a unit which runs the container in the Docker network "proxy" (e.g. behind the proxy project) and reads its configuration from "/srv/http/reverse-proxy-middleware/configuration.json".

Configuration

On start, the defaults under the key "configuration" in package.json are extended by "configuration.json" and then by "secure-configuration.json" from the current working directory. Both files are optional, the second one is meant for secrets. The top level options are:

  • "port" (default: the environment variable "PORT" or "8080"): where the proxy listens.
  • "host" (default empty, meaning all network interfaces): the address to listen on, e.g. "127.0.0.1".
  • "forwarders": the backends, see below.
  • "parseBody" (default "false"): parses JSON request bodies for expressions.
  • "logLevel" (default "info"): one of "debug", "info", "warn", "error" and "critical". "debug" logs every forwarded header.
  • "publicKeyPath" and "privateKeyPath": certificate and key files which switch the proxy to HTTPS, see below.
  • "nodeServerOptions": further options of the HTTPS server, see Node.js.

HTTPS

With "publicKeyPath" and "privateKeyPath" set, the proxy only accepts HTTPS connections. Relative paths start at the working directory, the files are read on start:

{
    "publicKeyPath": "certificate.pem",
    "privateKeyPath": "key.pem"
}

Encrypted connections always use HTTP/1.1. Certificate and key end up in "nodeServerOptions" as "cert" and "key" unless these are given there already.

Simple forwarding

This configuration passes every request on "http://localhost:8080" to "https://example.com" unchanged:

{
    "forwarders": {
        "example": {
            "host": "example.com"
        }
    }
}

curl --verbose http://localhost:8080

A forwarder has the following options, the defaults come from the special forwarder "base":

  • "host" (default "localhost"), "port" (default "443") and "tls" (default "true"): the backend.
  • "rejectUnauthorized" (default "false"): set it to "true" to only accept backends with a valid certificate.
  • "useExpression" (default "true"): decides whether this forwarder takes the request.
  • "headerTransformations": rewrites headers, see below.
  • "stateAPIs": requests to third party services, see below.

For a plain HTTP backend set "tls" to "false" and "port" to e.g. "80".

Distributing requests

Forwarders are tried in alphabetical order of their names. The first one whose "useExpression" results in "true" gets the request. This distributes requests randomly between two backends, like a basic load balancer:

{
    "forwarders": {
        "first": {
            "host": "first.example.com",
            "useExpression": "Math.random() < 0.5"
        },
        "second": {
            "host": "second.example.com"
        }
    }
}

Expressions can also route by path, e.g. "request.url.startsWith('/api/')". If no forwarder matches, the client gets status code "502".

Rewriting headers

"send" transformations apply to the request header sent to the backend, "retrieve" transformations to the response header sent back to the client. "source" is an expression resulting in a regular expression or string to search for, "target" one resulting in its replacement:

{
    "forwarders": {
        "example": {
            "host": "example.com",
            "headerTransformations": {
                "send": {
                    "source": "/X-Special-Client-Header-Name: (.+)/gi",
                    "target": "'New-Header-Name: $1'"
                },
                "retrieve": {
                    "source": "/set-cookie: (.+)/gi",
                    "target": "'X-Prevented-Cookie: $1'"
                }
            }
        }
    }
}

curl \
    --header 'X-Special-Client-Header-Name: value' \
    --output /dev/null \
    --verbose \
    http://localhost:8080

The backend gets "New-Header-Name: value" and every "set-cookie" header of the response arrives as "X-Prevented-Cookie". A transformation without "source" adds the header given by "target", e.g. "{"target": "'X-Forwarded-By: proxy'"}". The "host" header is always replaced by the backend's host.

State APIs

A state API is a request to a third party service which runs before the request is forwarded. Its "pre" expressions decide whether it runs, its "post" expressions evaluate its response. This forwarder only passes requests on if an authentication service accepts their token:

{
    "forwarders": {
        "example": {
            "host": "example.com",
            "stateAPIs": {
                "name": "authentication",
                "urlExpression": "`https://auth.example.com/check?token=${encodeURIComponent(request.headers['x-token'])}`",
                "options": {"headers": {"accept": "application/json"}},
                "expressions": {
                    "pre": "request.headers['x-token'] ? true : 401",
                    "post": "stateAPI.response?.ok ? null : 403"
                }
            }
        }
    }
}

Requests without an "X-Token" header are answered with "401", requests whose token the service rejects with "403", all others reach "example.com". The service is requested via fetch with the given "options". "url" sets a fixed address instead of "urlExpression".

"pre" and "post" accept a single expression or a list, which runs in order. The result of each "pre" expression means:

  • "true": run the request of this state API.
  • "false": skip this state API and its remaining "pre" expressions.
  • "'break'": stop evaluating "pre" expressions.
  • "null" or "undefined": continue with the next expression.
  • a number: answer the client with this status code and stop.

"post" expressions know the same results except "true" and "false". If no expression answers the client, the next state API runs and finally the request is forwarded.

Base configurations

Every forwarder inherits from the forwarder "base", and every state API of a forwarder inherits from its state API named "base". This configuration forwards to two backends under a sub path and asks one service with different data depending on the request:

{
    "forwarders": {
        "base": {
            "headerTransformations": {
                "send": {
                    "source": "/^(GET|POST) \\/(.*) (HTTP.*)$/m",
                    "target": "'$1 /sub/path/$2 $3'"
                }
            }
        },
        "first": {
            "host": "first.example.com",
            "useExpression": "Math.random() < 0.5"
        },
        "second": {
            "host": "second.example.com",
            "stateAPIs": [
                {
                    "name": "base",
                    "urlExpression": "`https://service.example.com/?q=${data.query}`",
                    "expressions": {
                        "pre": "request.headers[data.header] ? true : null",
                        "post": "stateAPI.response?.data?.allowed ? null : 403"
                    }
                },
                {
                    "name": "cats",
                    "data": {"header": "x-cats", "query": "cats"}
                },
                {
                    "name": "dogs",
                    "data": {"header": "x-dogs", "query": "dogs"}
                }
            ]
        }
    }
}

"data" holds any values for the expressions. JSON responses of state APIs are available as "stateAPI.response.data".

Expressions

Every expression is a JavaScript expression with access to:

  • "request": the client request with "url", "method" and "headers".
  • "response": the response to the client (not the one of a state API).
  • "stateAPI": the current state API with its "configuration", "error" and "response".
  • "stateAPIs": all state APIs of the forwarder by name, e.g. in header transformations.
  • "data": the state API's "data", the forwarder in "useExpression" and both sockets in header transformations.
  • "error": the error of a failed state API request.
  • "array", "datetime", "object", "string", "utility" and more: helpers of clientnode.

For example, this send transformation passes the answer of the authentication service from above on to the backend:

{
    "target": "`X-Allowed: ${stateAPIs.authentication.response?.data?.allowed}`"
}

Single values or lists

"headerTransformations.send", "headerTransformations.retrieve", "stateAPIs", "expressions.pre" and "expressions.post" take a single item or a list of items. "{...}" means the same as "[{...}]".

Environment variables

Any value of the configuration can be computed once on start with "evaluate", which has access to "environment" and "configuration":

{
    "forwarders": {
        "example": {
            "host": {
                "__evaluate__": "environment.BACKEND_HOST ?? 'example.com'"
            }
        }
    }
}

The proxy then forwards to the host given in the environment variable "BACKEND_HOST" or to "example.com". The default "port" works the same way with "PORT".

Development

yarn install
yarn check
yarn test
yarn serve:simple

"yarn check" checks types and lints, "yarn serve:<name>" builds the proxy and starts it with one of the configurations in "examples/" ("headers", "random", "simple" or "state-apis").
